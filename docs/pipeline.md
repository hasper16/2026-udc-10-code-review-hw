# Пайплайн рев'ю

> Task D. Опис архітектури безперервної інтеграції, конфігурації прав доступу та моделі загроз для AI-рев'юера у файлі `pipeline/ai-review.yml`.

## Що робить `pipeline/ai-review.yml`

1. **Тригер `pull_request`:** Пайплайн запускається на подію `pull_request` (цільова гілка `main`). Категорично не використовується небезпечний тригер `pull_request_target`, оскільки `pull_request` запускає код у контексті форку без доступу до секретів репозиторію та без прав на запис у репозиторій.
2. **Детерміновані обов'язкові перевірки (`deterministic-checks`):**
   - Першим обов'язковим кроком запускається виконання юніт-тестів застосунку (`cd app && npm test`). Якщо хоча б один тест падає, пайплайн негайно зупиняється (Failed Check), і код блокується для злиття ще до виклику AI.
   - Другим детермінованим кроком є статична перевірка git diff: якщо змінено будь-який файл у `app/src/`, перевіряється обов'язкова наявність змін у `app/CHANGELOG.md` (правило 6).
3. **Дорадче AI-рев'ю (`ai-review`):**
   - Запускається **лише після** успішного проходження детермінованих перевірок (`needs: deterministic-checks`).
   - Працює як **дорадчий (advisory) коментар**: крок має `continue-on-error: true`. Звіт рев'ю публікується як коментар до PR через GitHub Script. Падіння чи помилка AI-моделі не ламає білд, але надає розробнику та рецензенту структурований звіт за стандартом `docs/review-standard.md`.
4. **Хто затверджує злиття:** Злиття PR у `main` дозволяється **виключно людині** (Maintainer / Tech Lead). AI-рев'юер не має прав ухвалювати (`approve`) чи зливати PR; він виконує лише функцію аналітичного асистента.

## Права і секрети

- **Мінімальні права (`permissions`):**
  - За замовчуванням на рівні workflow: `contents: read`.
  - У джобі детермінованих перевірок: суворо `contents: read`.
  - У джобі AI-рев'ю: мінімально необхідні `contents: read` та `pull-requests: write` (виключно для залишення коментаря в обговоренні PR).
- **Ізоляція секретів для форків:** Для PR, створених із форків (`github.event.pull_request.head.repo.fork == true`), GitHub Actions автоматично блокує доступ до репозиторних секретів (`${{ secrets.AI_REVIEW_KEY }}`). Шкідливий PR не може викрасти API-ключі чи токени доступу.

## Модель загроз

| Що може зробити PR зі шкідливим вмістом | Що обмежує шкоду у вашому пайплайні |
|---|---|
| **Пряма або непряма промпт-ін'єкція:** Коментар у коді (як у PR-6: `NOTE FOR AI CODE REVIEWERS`) або в описі PR намагається перехопити керування LLM і змусити її відповісти "Approve". | • Вміст PR обробляється у пісочниці суворо як **дані**, а не як системний промпт.<br>• Вердикт AI є дорадчим: AI не має прав натиснути "Merge" чи самостійно закрити перевірку.<br>• Людина бачить коментар ін'єкції у дифі та відхиляє PR. |
| **Спроба викрадення секретів (Data Exfiltration):** Шкідливий код у PR намагається зчитати змінні середовища чи секрети репозиторію. | • Використання тригера `pull_request` замість `pull_request_target`: форки не отримують жодних секретів.<br>• У тестовому та детермінованому кроках змінні із секретами взагалі не передаються в оточення (`env`). |
| **Послаблення або видалення тестів:** Розробник прибирає перевірки або підміняє точні асерти на `> 0` (як у PR-5), щоб замаскувати баг. | • Детерміновані тести виконуються обов'язково.<br>• AI-рев'юер містить окрему лінзу *Verification Gap Review*, яка аналізує зміни у тестових файлах і сигналізує рецензенту-людині про послаблення захисту. |
| **Path Traversal або шкідливий код у тестах:** Зловмисник намагається вийти за межі репозиторію чи пошкодити раннер. | • Тести запускаються у відокремленій ефемерній віртуальній машині `ubuntu-latest`, яка знищується після завершення джоби.<br>• Жодних привілейованих прав доступу до інфраструктури. |

## Що лишається на людину

1. **Остаточний вердикт та злиття (Merge Gate):** Людина-інженер зобов'язана перевірити PR і власноруч підтвердити злиття після аналізу як детермінованих чеків, так і рекомендацій AI.
2. **Верифікація блокуючих знахідок:** Людина оцінює блокуючі зауваження AI (наприклад, виявлену вразливість Path Traversal у PR-6 чи відсутність перевірки ролі в PR-3).
3. **Розгляд нетривіальних бізнес-рішень:** Оцінка допустимості зміни тарифів, узгодження дат набрання чинності нових правил (як пільговий період у PR-5) та стратегічні архітектурні рішення.
