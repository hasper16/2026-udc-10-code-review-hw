# Code Review: PR-4 — Винести хелпери дат у src/dates.js

## 1. Резюме
PR переносить хелпери дат (`toUtc` → `toUtcMs`, `daysBetween`, `addDays`) з `app/src/loans.js` в новий модуль `app/src/dates.js`, `loans.js` реекспортує `addDays` і `daysBetween`, у `lateFee` локальну змінну `late` перейменовано на `daysLate`, додано `app/test/dates.test.js` і запис у `app/CHANGELOG.md`.

Я звірив код з базовою версією `app/src/loans.js`. Тіла функцій перенесено без змін логіки: формула `Date.UTC(...)` та сама, `Math.round(... / 86_400_000)` та сама, `toISOString().slice(0, 10)` та сама. Літерал `86_400_000` винесено в константу `MS_PER_DAY` з тим самим значенням. Усі внутрішні виклики (`borrow` → `addDays`, `lateFee`/`overdueReport` → `daysBetween`) тепер беруть функції з імпорту `./dates.js`. Наявний імпорт у `test/loans.test.js` (`addDays, daysBetween` з `../src/loans.js`) і далі працює завдяки реекспорту. Поведінка не змінюється, як і заявлено.

Директив, звернених до рев'юера, у PR немає. Блокуючих порушень не знайдено.

**Вердикт: СХВАЛЕНО (APPROVE).**

## 3. Зауваження та дрібниці (Non-blocking / Nits)
- **Реекспорт `toUtcMs`:** `loans.js` реекспортує лише `addDays` і `daysBetween`, а `toUtcMs` доступний тільки з `dates.js`. Це узгоджується з CHANGELOG і нічого не ламає, бо `toUtc` раніше не був публічним. Варто лише свідомо вирішити, чи `toUtcMs` має бути публічним API, чи лишитися внутрішнім хелпером модуля `dates.js`.
- **Подвійний імпорт/експорт у `loans.js`:** `import { addDays, daysBetween } from "./dates.js";` і `export { addDays, daysBetween } from "./dates.js";` стоять поруч. Так коректно, бо локальні виклики потребують імпорту. Можна лишити коментар, що реекспорт тимчасовий для зворотної сумісності, і в майбутньому перевести споживачів на `dates.js` (Правило 12, дрібниця).
- **Валідація входу (успадковано, не регресія):** `toUtcMs` не перевіряє формат рядка. Некоректний вхід (`"2026-1-5"`, `""`) дасть `NaN`, а `addDays` тоді кине `RangeError: Invalid time value`. Поведінка така сама, як у базі. Тепер модуль позиціонується як спільний для «учасників і звітів», тож варто колись додати валідацію `YYYY-MM-DD`.
- В опис PR варто додати, що `toUtc` перейменовано на `toUtcMs` і зроблено публічним. Зараз про це сказано лише в CHANGELOG.

## 4. Аналіз тестів та верифікації
- Нові тести перевіряють конкретні значення, а не лише форму результату (відповідає Правилу 8):
  - `addDays("2026-12-25", 14) === "2027-01-08"` — перехід через межу року;
  - `addDays("2026-02-20", 14) === "2026-03-06"` — перехід через кінець лютого невисокосного року;
  - `daysBetween("2026-10-08", "2026-10-01") === -7` — від'ємний результат;
  - `toUtcMs("2026-10-08")` → `"2026-10-08T00:00:00.000Z"`.
- Наявні тести в `test/loans.test.js` (`addDays("2026-09-25", 14)`, `daysBetween("2026-09-24", "2026-10-08") === 14`) залишились і через реекспорт перевіряють сумісність старого шляху імпорту.
- Правило 9 не застосовується: нові функції не мають перевірки доступу.
- **Верифікаційні розриви (неблокуючі):**
  - Тест «toUtcMs ignores the local time zone» не змінює часову зону процесу, наприклад через запуск з `TZ=Pacific/Kiritimati` / `TZ=America/Los_Angeles`. Тому він не доводить незалежність від TZ, лише коректність UTC-значення в поточному середовищі. Реалізація через `Date.UTC` від TZ і так не залежить.
  - Немає тесту на 29 лютого високосного року (наприклад, `addDays("2028-02-20", 14) === "2028-03-05"`) і на `daysBetween` через межу року чи переходу на літній час (наприклад, `"2026-03-28"` → `"2026-03-30"`).
  - Немає тесту з `days = 0` або від'ємним `days` для `addDays`.
