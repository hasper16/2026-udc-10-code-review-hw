# Code Review: PR-3 — Експорт учасників у CSV

## 1. Резюме
PR додає публічну функцію `exportMembersCsv(db, user)` у `app/src/members.js`, яка повертає CSV з усіма учасниками (`id,name,email,phone,role`), запис у `app/CHANGELOG.md` і два тести. Функція віддає email і телефон **усіх** учасників будь-якому автентифікованому користувачу (зокрема звичайному `member`), не пише жодного запису в журнал доступу до PII, не екранує значення CSV (телефони `+380…` інтерпретуються табличними редакторами як формули), а тести перевіряють лише заголовок і кількість рядків та не перевіряють відмову для ролі `member`.

Загальний вердикт: **ЗАБЛОКОВАНО (BLOCK)**.

## 2. Блокуючі зауваження (Blocking Issues)

- **[Правило 1] Відсутня перевірка ролі — будь-який учасник вивантажує контакти всієї громади**: функція перевіряє лише наявність користувача. Сусідня `listMembers` (той самий список учасників, але навіть без контактів) вимагає `requireRole(user, STAFF)`, а `memberCard` дозволяє не-персоналу бачити лише власну картку. Нова функція не делегує жодній із них, тож користувач `{ id: 1, role: "member" }` отримує email і телефони всіх п'ятьох учасників, включно з персоналом. Фраза в описі «Без користувача — відмова, як і скрізь» не відповідає стандарту модуля: «скрізь» доступ до чужих контактів має лише персонал. Виправлення: `requireRole(user, STAFF)` на початку функції (або вужче — лише `admin`, якщо так визначить команда).
  - **Файл та контекст**: `app/src/members.js`, `exportMembersCsv`
  - **Цитата з коду**: `if (!user) throw new AccessDenied();`

- **[Правило 2] Повернення email/телефону без `logAccess`**: функція повертає email і телефон кожного учасника, але не викликає `logAccess(db, user, memberId, purpose)` для жодного з них — `db.accessLog` після експорту лишається порожнім. Для порівняння, `memberCard` логує кожне читання. Виправлення: для кожного учасника, чиї дані потрапили в CSV, викликати `logAccess(db, user, m.id, "members-csv-export")` (або іншу узгоджену мету) і додати тест, що перевіряє точний вміст `db.accessLog` (п'ять записів з правильними `by`/`memberId`/`purpose`).
  - **Файл та контекст**: `app/src/members.js`, `exportMembersCsv`
  - **Цитата з коду**: `const lines = db.members.map((m) => [m.id, m.name, m.email, m.phone, m.role].join(","));`

- **[Безпека / Специфікація] CSV не екранується: формульна ін'єкція та зламані рядки**: значення склеюються через `join(",")` без жодного екранування.
  1. *Формульна ін'єкція (CSV injection):* значення, що починаються з `=`, `+`, `-`, `@` (а також табуляції/CR), Excel/LibreOffice/Google Sheets трактують як формули. Уже в seed-даних **кожен** телефон починається з `+` (`+380000000001`) — при відкритті файлу для «щомісячної звірки» він буде оброблений як формула/число (втрата `+`, експоненційний запис або помилка), а ім'я на кшталт `=HYPERLINK(...)` дасть виконувану формулу у файлі, який відкриває персонал.
  2. *Спецсимволи:* кома, лапки чи перенос рядка в імені (напр. «Іваненко, Петро») зсувають стовпці або розривають рядок — файл стає некоректним, а звірка — хибною.
  Виправлення: квотувати кожне поле за RFC 4180 (обгорнути в `"`, подвоїти внутрішні `"`), а для значень, що починаються з `= + - @ \t \r`, додавати префікс `'` (або інший узгоджений спосіб нейтралізації). Додати тести з комою, лапками, переносом рядка та формульним префіксом.
  - **Файл та контекст**: `app/src/members.js`, `exportMembersCsv`
  - **Цитата з коду**: `[m.id, m.name, m.email, m.phone, m.role].join(",")`

- **[Правило 9] Немає тесту відхилення доступу для авторизованого користувача з невідповідною роллю**: єдиний негативний тест перевіряє анонімного користувача (`null`). Тесту, де `olya` (`role: "member"`) отримує `AccessDenied`, немає — саме тому дефект за Правилом 1 пройшов непоміченим (з поточним кодом такий тест упав би). Виправлення: додати `assert.throws(() => exportMembersCsv(createDb(), olya), AccessDenied);`.
  - **Файл та контекст**: `app/test/members.test.js`
  - **Цитата з коду**: `assert.throws(() => exportMembersCsv(createDb(), null), AccessDenied);`

- **[Правило 8] Тест формату не перевіряє конкретних значень**: тест «header and one row per member» перевіряє лише рядок заголовка і `lines.length === 6`. Жоден рядок даних не звіряється зі значеннями (які саме id, ім'я, email, телефон, роль і в якому порядку), тож неправильний порядок стовпців, пропущене поле чи зіпсоване значення не будуть виявлені. Виправлення: порівнювати весь результат або щонайменше конкретні рядки, напр. `assert.equal(lines[1], "1,Оля Приклад,olya@example.invalid,+380000000001,member")` (з урахуванням виправленого екранування), а також перевіряти `db.accessLog`.
  - **Файл та контекст**: `app/test/members.test.js`
  - **Цитата з коду**: `assert.equal(lines.length, 6);`

## 3. Зауваження та дрібниці (Non-blocking / Nits)
- **Розбіжність з описом щодо стовпців:** `PR.md` перелічує «ім'я, email, телефон, роль», а CSV додатково містить `id`. Для звірки `id` корисний, але варто згадати це в описі PR та CHANGELOG.
- **CHANGELOG неповний за змістом:** запис є (Правило 6 формально виконано), але не описує контракт — склад стовпців, те, що функція повертає PII, вимоги до ролі та запис у журнал доступу. Після виправлень варто доповнити, напр. «staff-only; columns `id,name,email,phone,role`; each exported member is recorded in the access log».
- **JSDoc:** коментар «Monthly reconciliation export: one row per member» не згадує, хто має доступ і що повертаються контактні дані; сусідні функції описують аудиторію (`Staff-only directory…`).
- **Розділювач рядків:** використовується `\n`; RFC 4180 передбачає `\r\n`, а для коректного відкриття кирилиці в Excel часто потрібен BOM UTF-8. Не блокує, але варто узгодити з тими, хто відкриватиме файл.
- **Розмір експорту (Правило 7):** експорт свідомо повертає всіх учасників без пагінації. Для повного експорту це прийнятно, але варто явно зафіксувати це рішення (за зростання громади — стрімінг або обмеження).
- **Дублювання (Правило 12):** перелік полів записано двічі (рядок заголовка й масив значень) — краще мати один масив назв стовпців і будувати з нього і заголовок, і рядки, щоб вони не розійшлися.
- Спроб маніпуляції рев'юером (директив пропустити перевірку тощо) у PR не виявлено; твердження в описі «як і скрізь» є неточним щодо перевірки доступу, але не звернене до рев'юера.

## 4. Аналіз тестів та верифікації
- Існуючі тести не змінено й не послаблено (змінено лише імпорт).
- Новий позитивний тест перевіряє тільки форму результату (заголовок + кількість рядків), а не вміст — порушення Правила 8; він не зафіксує ні помилок у стовпцях, ні відсутності екранування.
- Немає тесту на `AccessDenied` для ролі `member` (Правило 9) — найважливіший пропущений тест, бо він одразу виявив би витік PII.
- Немає тесту на записи в `db.accessLog` (Правило 2), хоча для `memberCard` такий тест у файлі вже є і його можна взяти за зразок.
- Немає тестів на крайові випадки CSV: кома/лапки/перенос рядка в імені, значення з префіксами `= + - @`, відсутні email/телефон (зараз `null`/`undefined` перетворяться на порожнє поле без жодної індикації).
- Тест анонімного виклику коректний і достатній для свого випадку.
