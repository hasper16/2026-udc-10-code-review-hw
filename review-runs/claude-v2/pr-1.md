# Code Review: PR-1 — Сторінкування для списку позик

## 1. Резюме
PR додає публічну функцію `listLoansPage(db, user, { page, pageSize })`, яка делегує вибірку наявній `listLoans` і повертає `{ items, page, pageSize, total }`. Делегування авторизації коректне (`listLoans` уже розмежовує дані за роллю), проте сама пагінація зламана: зсув обчислюється як `page * pageSize` при 1-базовій нумерації (дефолт `page = 1`), тому перша сторінка ніколи не повертається, а `page = 1` віддає другу. Межі параметрів не валідуються, розмір сторінки не обмежено, запису в `app/CHANGELOG.md` немає, а новий тест не перевіряє, які саме елементи повернуто (тому й не ловить off-by-one).

**Вердикт: ЗАБЛОКОВАНО (BLOCK).**

## 2. Блокуючі зауваження (Blocking Issues)

- **[Правило 7] Off-by-one у розрахунку зсуву — перша сторінка недосяжна через 1-базовий номер**: дефолт `page = 1` означає 1-базову нумерацію, але зсув рахується як `page * pageSize`. Підстановка меж:
  - `page = 1, pageSize = 20` → `start = 20` → `slice(20, 40)`: повертаються позики з індексами 20–39 (21-ша…40-ва), тобто **друга** сторінка. На тестовій базі з 7 позик — **порожній** `items` при `total: 7`.
  - Перші 20 записів (індекси 0–19) доступні лише через `page = 0`, якого API не заявляє.
  - Остання сторінка: при 7 позиках і `pageSize = 5` реальна друга сторінка (індекси 5–6) приходить на `page = 1`, а `page = 2` → `start = 10` → порожньо. Для 3 000+ рядків UI, що йде від 1 до `ceil(total/pageSize)`, ніколи не покаже перші `pageSize` позик, а остання сторінка буде порожньою.
  - Виправлення: `const start = (page - 1) * pageSize;`.
  - **Файл та контекст**: `app/src/loans.js`, `listLoansPage`
  - **Цитата з коду**: `const start = page * pageSize;`

- **[Правило 7] Відсутня валідація та обмеження `page`/`pageSize`**: параметри приймаються як є. `pageSize = 1_000_000` повертає весь список (сторінкування, заради якого PR існує, обходиться одним параметром); `pageSize = 0` → завжди порожньо; від'ємні значення дають негативний `start`, і `Array.prototype.slice` інтерпретує його як відлік від кінця (напр. `page = -1, pageSize = 20` → `slice(-20, 0)` → порожньо; `page = 0`, як показано вище, — фактична перша сторінка). Нецілі/`NaN` значення (`"2"`, `1.5`) теж не відсікаються, а `page` у відповіді відлунює некоректне значення. Потрібно: `page` — ціле ≥ 1, `pageSize` — ціле в межах `1..MAX_PAGE_SIZE` (наприклад, 100), інакше помилка або затискання до меж.
  - **Файл та контекст**: `app/src/loans.js`, `listLoansPage`
  - **Цитата з коду**: `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {`

- **[Правило 6] Нова публічна функція без запису в CHANGELOG**: `listLoansPage` експортується з `src/loans.js` і розширює публічний API, але `app/CHANGELOG.md` у дифі не змінено. Додайте запис із сигнатурою, семантикою `page` (1-базова), меж `pageSize` та формою відповіді `{ items, page, pageSize, total }`.
  - **Файл та контекст**: `app/src/loans.js` / `app/CHANGELOG.md` (відсутня зміна)
  - **Цитата з коду**: `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {`

- **[Правило 8] Новий тест не перевіряє конкретні повернені елементи**: тест стверджує лише `total`, `page` і `pageSize` — значення, які функція просто відлунює або бере з `all.length`. Вміст `items` не перевіряється взагалі, тому тест проходить, хоча `items` на `page: 1` — порожній масив. Потрібні твердження на кшталт `assert.deepEqual(res.items.map((l) => l.id), [1, 2, 3, 4, 5, 6, 7])` для першої сторінки, а також тест з малим `pageSize` (напр. `pageSize: 5` → сторінка 1 = `[1..5]`, сторінка 2 = `[6, 7]`), тести на межі (останню сторінку, сторінку за межами діапазону) та на відхилення некоректних `page`/`pageSize`.
  - **Файл та контекст**: `app/test/loans.test.js`, тест `paged list reports the total and the page it returned`
  - **Цитата з коду**: `assert.equal(res.total, 7); assert.equal(res.page, 1); assert.equal(res.pageSize, 20);`

## 3. Зауваження та дрібниці (Non-blocking / Nits)
- **Точність JSDoc (Правило 10, nit)**: коментар каже «Paged variant for the staff UI», але функція через `listLoans` доступна й учасникам (member бачить свої позики посторінково). Делегування коректне й безпечне — це лише неточність опису; варто написати «Staff see every loan; a member sees only their own» за аналогією з `listLoans`.
- **Ефективність**: `listLoans` копіює всі рядки (`rows.map((l) => ({ ...l }))`) перед `slice`, тож для 3 000+ рядків на кожну сторінку копіюється весь список. Для заявленої мети («UI гальмує») краще спершу відфільтрувати/вирізати сторінку, а копіювати лише її елементи (можна винести спільну приватну функцію фільтрації за роллю, щоб не дублювати логіку).
- **Порядок**: стабільність порядку сторінок залежить від порядку `db.loans`; варто явно зафіксувати сортування (наприклад, за `id`), щоб сторінки не «пливли» між запитами при зміні сховища.
- Опис PR («Тест додав») не згадує ані семантику нумерації сторінок, ані обмеження розміру — варто доповнити.

## 4. Аналіз тестів та верифікації
- Наявні тести не послаблено: тест «staff see every loan» залишився з точним значенням `7`; змінено лише імпорт.
- Новий тест має верифікаційний розрив: перевіряє лише метадані відповіді, не вміст `items`. Через це off-by-one у зсуві (`page * pageSize`) залишився непоміченим — на тестовій базі `page: 1` повертає `items: []`, а тест зелений.
- Відсутні тести меж пагінації: перша/остання сторінка, сторінка за межами, `pageSize` = 0/від'ємний/надвеликий, `page` = 0/від'ємний.
- Немає тесту для учасника (member): що `listLoansPage` для `olya` повертає лише `[1, 2, 7]` і `total: 3` — це закріпило б коректне делегування авторизації.
- Правило 9: функція не має власної перевірки `requireRole`, а делегує `listLoans`, тому обов'язкового тесту на `AccessDenied` не вимагається; проте тест на `user = null` (`/user required/`) був би корисним.
- Інструкцій/директив, звернених до рев'юера, у PR не виявлено (Правило 11 — без зауважень).
