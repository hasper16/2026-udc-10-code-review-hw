# Code Review: PR-5 — Пільговий день для штрафу за прострочення

## 1. Резюме
PR додає константу `GRACE_DAYS = 1` та зменшує кількість днів прострочення у функції `lateFee()`, а також змінює два існуючі тести в `app/test/loans.test.js` і додає запис у `app/CHANGELOG.md`.

Проте реалізація суперечить заявленій специфікації («нова політика з 1 листопада» застосована безумовно до всіх дат, включно з минулими позиками за жовтень), а існуючі тести, які впали через цю помилку, були штучно послаблені замість виправлення логіки.

Загальний вердикт: **ЗАБЛОКОВАНО (BLOCK)**.

## 2. Блокуючі зауваження (Blocking Issues)

- **[Правило 10] Відповідність коду опису PR (відсутність перевірки дати початку дії політики)**: В описі `PR.md`, у `app/CHANGELOG.md` та в коментарі в коді прямо зазначено, що нова політика («перший день прострочення безкоштовний») діє **з 1 листопада** (`2026-11-01`). Проте у функції `lateFee` віднімання `GRACE_DAYS` виконується безумовно для будь-яких дат. Через це нова політика ретроактивно змінює розрахунок штрафів для жовтневих та старіших позик (зокрема тих, що перевірялися в існуючих тестах станом на `2026-10-08`). Необхідно додати перевірку дати початку дії політики (наприклад, застосовувати `GRACE_DAYS` лише якщо `loan.dueAt >= "2026-11-01"` або `loan.takenAt >= "2026-11-01"` відповідно до бізнес-вимог).
  - **Файл та контекст**: `app/src/loans.js`
  - **Цитата з коду**:
    ```javascript
    export const GRACE_DAYS = 1; // політика з 1 листопада: перший день прострочення безкоштовний
    ...
    export function lateFee(loan, onIso) {
      const late = daysBetween(loan.dueAt, loan.returnedAt ?? onIso) - GRACE_DAYS;
      return late > 0 ? late * FEE_PER_DAY_KOPECKS : 0;
    }
    ```

- **[Правило 8] Строгість і повнота перевірок у тестах (послаблення існуючих тестів та відсутність тестів на нову логіку)**: Замість того, щоб з'ясувати, чому впали жовтневі тести (через відсутність перевірки дати `2026-11-01`), автор замінив точні перевірки фінансових сум `assert.equal(..., 1500)` та `assert.equal(..., 11000)` на нестрогі перевірки `assert.ok(... > 0)`. Це прямо порушує Правило 8, яке категорично забороняє послаблювати існуючі тести та використовувати абстрактні перевірки виду `assert.ok(val > 0)` замість конкретних очікуваних значень. Крім того, у PR взагалі не додано жодного тесту, який би перевіряв саму нову функціональність пільгового дня (наприклад, що рівно 1 день прострочення дає `0` копійок штрафу, а 3 дні прострочення після 1 листопада — `1000` копійок).
  - **Файл та контекст**: `app/test/loans.test.js`
  - **Цитата з коду**:
    ```javascript
    -  assert.equal(lateFee(returnedLate, "2026-10-08"), 1500);
    +  assert.ok(lateFee(returnedLate, "2026-10-08") > 0);
    ...
    -  assert.equal(rows[0].feeKopecks, 11000);
    +  assert.ok(rows[0].feeKopecks > 0);
    ```

## 3. Зауваження та дрібниці (Non-blocking / Nits)
- **Узгодженість `daysLate` та `feeKopecks` у `overdueReport`**: У функції `overdueReport` (`app/src/loans.js`) поле `daysLate` обчислюється як `daysBetween(l.dueAt, todayIso)`, тоді як `feeKopecks` викликає `lateFee(l, todayIso)` з урахуванням `GRACE_DAYS`. Якщо клієнтська сторона або персонал очікує, що у звіті за прострочення на 1 день (коли `daysLate === 1`) штраф дорівнюватиме `0` копійок, це варто явно задокументувати або покрити тестом, щоб уникнути плутанини між кількістю днів прострочення та кількістю оплачуваних днів.

## 4. Аналіз тестів та верифікації
- **Критичний верифікаційний розрив (Verification Gap)**: Послаблення `assert.equal(..., 1500)` та `assert.equal(..., 11000)` до `assert.ok(... > 0)` повністю руйнує здатність тестів виявляти помилки в розрахунку тарифів (будь-яке додатне число від `1` до `99999999` пройде тест).
- **Відсутність граничних тестів (Edge Cases)**:
  - Відсутній тест на граничний випадок `1 день прострочення` (коли `daysBetween === 1` і штраф за новою політикою має становити `0`, а не `500`).
  - Відсутній тест на перехід дати `2026-11-01` (порівняння розрахунку до 1 листопада та з 1 листопада).
- Необхідно повернути точні перевірки `assert.equal(..., 1500)` і `assert.equal(..., 11000)` для існуючих жовтневих тестів та додати окремий тест для листопадової політики з перевіркою точних сум у копійках (`0` для 1 дня прострочення, `1000` для 3 днів тощо).
