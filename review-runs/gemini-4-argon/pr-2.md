# Code Review: PR-2 — Email учасника у звіті про прострочення

## 1. Резюме
PR додає поле `email` до рядків звіту `overdueReport`, проте містить низку критичних порушень стандартів безпеки, фінансового контракту API та ведення документації:
1. Відсутній обов'язковий аудит доступу до персональних даних (`logAccess`) при поверненні `email` (Правило 2).
2. Додано форматований рядок грошової суми `feeText` («... грн») у `src/`, що прямо заборонено стандартом фінансових даних (Правило 4) і є несанкціонованим розширенням функціональності (Scope Creep, Правило 10).
3. Розширення контракту публічної функції `overdueReport` не зафіксовано в `app/CHANGELOG.md` (Правило 6).

Вердикт: **ЗАБЛОКОВАНО (BLOCK)**.

## 2. Блокуючі зауваження (Blocking Issues)

- **[Правило 2] Відсутній аудит доступу до персональних даних (`logAccess`) при поверненні `email`**: Email є конфіденційними персональними даними (PII). Згідно з правилами команди, кожна функція, що повертає `email` або `phone`, зобов'язана викликати `logAccess(db, user, memberId, purpose)` з `src/audit.js` окремо для кожного учасника, чиї контактні дані повертаються (навіть якщо функція доступна лише для персоналу). Необхідно імпортувати `logAccess` у `app/src/loans.js` та логувати доступ для кожного знайденого учасника у звіті.
  - **Файл та контекст**: `app/src/loans.js` (функція `overdueReport`)
  - **Цитата з коду**:
    ```js
          member: db.findMember(l.memberId)?.name ?? "—",
          email: db.findMember(l.memberId)?.email ?? null,
    ```

- **[Правило 4, Правило 10] Порушення формату фінансових даних в API та несанкціонований Scope Creep (`feeText`)**: У публічному API суми грошей мають передаватися виключно в цілих копійках (`...Kopecks`). Форматування сум у рядки для відображення людині (`"110,00 грн"`) у шарі `src/` категорично заборонено (Правило 4). Крім того, додавання поля `feeText` взагалі не згадується в описі `PR.md`, що є прихованим розширенням задачі (Scope Creep, Правило 10). Поле `feeText` потрібно повністю видалити.
  - **Файл та контекст**: `app/src/loans.js` (функція `overdueReport`)
  - **Цитата з коду**:
    ```js
          feeKopecks: lateFee(l, todayIso),
          feeText: (lateFee(l, todayIso) / 100).toFixed(2).replace(".", ",") + " грн",
    ```

- **[Правило 6] Відсутній запис у `app/CHANGELOG.md` про зміну контракту `overdueReport`**: Публічна функція `overdueReport(db, user, todayIso)` тепер повертає нове поле `email` у кожному елементі результату (раніше в `app/CHANGELOG.md` було явно зафіксовано перелік полів: `loanId`, `member`, `book`, `daysLate`, `feeKopecks`). Будь-яка зміна значень, які повертає публічна функція в `src/`, має супроводжуватися оновленням `app/CHANGELOG.md` у тому самому PR.
  - **Файл та контекст**: `app/CHANGELOG.md` / `review-queue/pr-2/change.diff`
  - **Цитата з коду**:
    ```markdown
    - `overdueReport(db, user, todayIso)` — staff-only report of loans past due, with
      `loanId`, `member`, `book`, `daysLate`, `feeKopecks`.
    ```

## 3. Зауваження та дрібниці (Non-blocking / Nits)
- **[Правило 12] Повторні пошукові виклики в одній ітерації (Fowler Smells — Duplicate Lookup / Repeated Computation)**:
  - Усередині `.map((l) => ...)` двічі поспіль викликається `db.findMember(l.memberId)` для одного й того самого позичання — спочатку для `name`, потім для `email` (причому попередню оптимізацію зі словником `Map` було видалено). Варто знайти учасника один раз на ітерацію (`const m = db.findMember(l.memberId);`) або побудувати `Map` учасників перед циклом.
  - Функція `lateFee(l, todayIso)` також викликалася двічі на кожну ітерацію (для `feeKopecks` і `feeText`). Після видалення `feeText` це дублювання зникне.
- **Актуальність JSDoc**: Коментар над `overdueReport` у `app/src/loans.js` (`with the member's name. Built for the weekly reminder calls.`) варто оновити, щоб він відображав наявність `email`.

## 4. Аналіз тестів та верифікації
- У `app/test/loans.test.js` додано перевірку `assert.equal(rows[0].email, "marko@example.invalid");`, яка перевіряє лише наявність поля `email` у першому рядку звіту.
- **Верифікаційний розрив (Verification Gap)**: Відсутній тест (або перевірка в існуючому тесті), який детерміновано контролює запис у `db.accessLog` при виклику `overdueReport` (перевірка того, що для кожного повернутого у звіті учасника з `email` створено відповідний запис аудиту з `by: iryna.id`, `memberId` та коректним `purpose`).
