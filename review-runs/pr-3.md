# Code Review: PR-3 — Експорт учасників у CSV

## 1. Резюме
PR додає функцію `exportMembersCsv` для вивантаження бази учасників (включно з email та номерами телефонів) у форматі CSV для щомісячної звірки. Реалізація містить критичну вразливість авторизації (доступ відкрито будь-якому автентифікованому звичайному учаснику), повну відсутність обов'язкового аудиту персональних даних, наївне формування CSV без екранування, а також фіктивний тест на безпеку, який замаскував відсутність перевірки ролі.
**Вердикт: ЗАБЛОКОВАНО (Changes Requested)**.

## 2. Блокуючі зауваження (Blocking Issues)

### 1. [Правило 1 / Стандарт & Безпека] Критичне порушення контролю доступу (Privilege Escalation)
- **Файл**: `app/src/members.js:10`
- **Цитата з коду**:
  ```javascript
  export function exportMembersCsv(db, user) {
    if (!user) throw new AccessDenied();
  ```
- **Проблема**: Функція перевіряє лише факт наявності об'єкта `user`, але взагалі не перевіряє роль (`role`). Відповідно, будь-який зареєстрований читач (`role: "member"`, наприклад, користувач Оля) може викликати цю функцію і отримати повний дамп контактних даних усіх учасників бібліотеки. Це пряме порушення правила 1 домовленостей команди: *«Кожна функція, що віддає дані, перевіряє роль — так само, як сусідні функції того самого модуля.»* Сусідня функція `listMembers` вимагає `requireRole(user, STAFF)`.
- **Виправлення**: Застосувати перевірку ролі персоналу або адміністратора:
  ```javascript
  requireRole(user, STAFF);
  ```

### 2. [Правило 2 / Стандарт] Масовий витік PII без фіксації в журналі аудиту (`logAccess`)
- **Файл**: `app/src/members.js:12`
- **Цитата з коду**:
  ```javascript
  const lines = db.members.map((m) => [m.id, m.name, m.email, m.phone, m.role].join(","));
  ```
- **Проблема**: Функція повертає `email` та `phone` для всіх учасників одночасно. Пункт 2 домовленостей команди зобов'язує: *«Email і телефон учасника — персональні дані. Будь-яка функція, що їх повертає, записує доступ у журнал: `logAccess(db, user, memberId, purpose)` з `src/audit.js`, один запис на кожного учасника, чиї дані віддано.»* У поточному коді запис в `accessLog` не виконується взагалі.
- **Виправлення**: Перед поверненням або під час генерації рядків зафіксувати доступ для кожного експортованого учасника:
  ```javascript
  for (const m of db.members) {
    logAccess(db, user, m.id, "monthly-reconciliation-csv");
  }
  ```

### 3. [Правило 9 / Verification Gap] Неповноцінний тест на відхилення доступу
- **Файл**: `app/test/members.test.js:60-62`
- **Цитата з коду**:
  ```javascript
  test("CSV export refuses an anonymous caller", () => {
    assert.throws(() => exportMembersCsv(createDb(), null), AccessDenied);
  });
  ```
- **Проблема**: Автор додав тест лише для анонімного виклику (`null`), але не перевірив доступ з боку звичайного учасника (`olya = { id: 1, role: "member" }`). Це пряме порушення правила 9 стандарту: *«Нова функція з перевіркою доступу має тест, де доступ відхилено [для неавторизованого користувача].»* Саме відсутність тесту на відхилення ролі `member` дозволила вразливості авторизації потрапити в PR.
- **Виправлення**: Додати тест, який перевіряє, що `exportMembersCsv(createDb(), olya)` викидає `AccessDenied`.

## 3. Зауваження та дрібниці (Non-blocking / Nits)

### 1. [Edge Case Hunter / Безпека даних] Наївне формування CSV (відсутність екранування)
- **Файл**: `app/src/members.js:12`
- Об'єднання значень через простий `.join(",")` вразливе до ламання структури файлу та CSV Injection, якщо ім'я або інше поле містить кому (`,`), лапки (`"`) чи символ нового рядка (`\n`). Значення слід обгортати в лапки з екрануванням подвійних лапок згідно з RFC 4180.
